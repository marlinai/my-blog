## 1. 版本控制与 Git 底层哲学

### 1.1 集中式 vs 分布式
在深入命令之前，我们需要理解 Git 的本质。传统的版本控制系统（如 SVN）是**集中式**的，版本库集中存放在中央服务器上，每次代码提交、查看历史都需要联网与中央服务器交互。一旦服务器宕机，整个团队的开发就会陷入瘫痪。

Git 是**分布式**版本控制系统。每一个克隆出来的仓库都是一个极其完整的版本库，包含了所有的历史记录。这意味着：
- **绝大多数操作本地化**：提交、查看历史、创建分支都在本地瞬时完成，无需联网。
- **天然的分布式备份**：每个开发者的电脑上都有一份完整的代码库副本，中央服务器崩溃也可以轻松用任何一个本地仓库进行恢复。

### 1.2 Git 的三大分区
Git 的内部构造可以精简为三个核心区域，理解这三个区域的数据流动是掌握 Git 的钥匙：

```
 +------------------+        git add        +------------------+
 |  工作区           | -------------------> |  暂存区 (Index)  |
 |  (Working Dir)   |                      |  (Staging Area)  |
 +------------------+                      +------------------+
          ^                                         |
          |               git checkout              | git commit
          |               (或 git restore)          v
 +-------------------------------------------------------------+
 |                       本地仓库 (.git dir)                   |
 |                       (Local Repository)                    |
 +-------------------------------------------------------------+
```

1. **工作区 (Working Directory)**：你在电脑里实际看到的目录和文件。你在这里直接修改、增加或删除代码。
2. **暂存区 (Staging Area / Index)**：一个隐藏的临时存盘点。它是工作区通往本地仓库的“检票口”，允许你对要提交的修改进行精细组装和筛选。
3. **本地仓库 (Repository)**：存储在项目根目录下隐藏的 `.git` 文件夹中。这里保存着你提交的所有版本历史和元数据，是 Git 的核心。

### 1.3 Git 的数据模型：快照而非增量
许多版本控制系统存储的是文件的**增量变化（Delta）**，即文件每次改动了哪些行。
而 Git 采取了截然不同的**快照（Snapshot）**设计思想。每次你提交更新时，Git 都会对当前全部文件制作一个快照，并保存这个快照的索引。如果文件没有修改，Git 不会重新保存该文件，而是直接链接到上一个已存储的相同文件。这种设计使得 Git 在分支切换和版本回滚时拥有无与伦比的速度。

## 2. Git 基础：从零开始的单兵作战

### 2.1 环境配置
在开始使用 Git 之前，首要任务是配置你的身份标识（自报家门）。每一次 Git 提交都会使用这些信息，并随提交一同永久注入历史记录中。

```bash
# 配置全局用户名
git config --global user.name "Your Name"

# 配置全局用户邮箱
git config --global user.email "your_email@example.com"

# 查看当前的所有配置列表
git config --list

# 仅查看某一项配置
git config user.name
```
> **提示**：`--global` 参数代表这些配置将应用在你系统上的所有 Git 仓库中。如果你希望针对某个特定的商业项目使用不同的邮箱，可以在该项目目录下不加 `--global` 重新配置。

### 2.2 仓库初始化与克隆
有两种方式可以让你拥有一个本地 Git 仓库：

**方式一：本地全新初始化**
```bash
# 进入你的项目目录
cd /path/to/your/project

# 将当前目录初始化为 Git 仓库
git init
```
执行后，项目根目录下会生成一个隐藏的 `.git` 文件夹，不要手动修改它，它是 Git 的核心大脑。

**方式二：克隆已有仓库**
```bash
# 从远程托管平台（GitHub/GitLab等）克隆一个项目到本地
git clone https://github.com/user/repository.git

# 克隆并指定本地文件夹名称
git clone https://github.com/user/repository.git my_project_name
```

### 2.3 核心单兵命令
在日常开发中，以下四个命令组成了最频繁的数据循环：

```bash
# 1. 查看当前仓库的状态（哪些文件被修改了、哪些在暂存区）
git status

# 2. 将修改过的或新创建的文件追踪并添加到暂存区
git add filename.py        # 添加单个文件
git add src/               # 添加整个文件夹
git add .                  # 添加当前目录下的所有修改和新文件

# 3. 将暂存区的内容提交到本地仓库，并撰写有意义的提交信息
git commit -m "feat: 增加用户登录接口及单元测试"

# 4. 查看提交历史日志
git log
```

### 2.4 日常状态精细查看
`git status` 虽然好用，但有时信息不够紧凑，或者无法直观看到具体改动了哪几行代码。

```bash
# 简短极简状态显示
git status -s

# 查看工作区与暂存区之间具体代码行的差异（还没 add 的改动）
git diff

# 查看暂存区与上一次提交之间的代码行差异（已经 add 还没 commit 的改动）
git diff --cached
```

## 3. 分支艺术：并行开发的黄金法则

分支是 Git 最具威力的特性。得益于其底层独特的指针设计，Git 创建、切换和删除分支几乎在瞬间完成，这鼓励开发者大量使用**短期特性分支**。

### 3.1 分支的基本物理形态
在 Git 中，分支本质上只是一个指向某个提交对象（Commit Object）的**可变指针**。Git 的默认分支名称通常是 `main` 或 `master`。Git 还有一个名为 `HEAD` 的特殊指针，它就像是“你当前所在的视点”，指向你当前正在工作、浏览的分支。

```
                    HEAD
                     |
                   feature
                     |
[Commit A] <-- [Commit B] <-- [Commit C]
                                 ^
                                 |
                               main
```

### 3.2 分支的基础操作
```bash
# 创建一个名为 feature-login 的新分支（此时 HEAD 还在原分支）
git branch feature-login

# 切换到指定分支
git checkout feature-login
# 【现代 Git 推荐命令】功能更专一的切换分支命令：
git switch feature-login

# 创建并直接切换到新分支（合并一步完成）
git checkout -b feature-payment
# 【现代 Git 推荐命令】：
git switch -c feature-payment

# 列出本地所有分支（当前所在分支前会带 * 号）
git branch

# 列出本地和远程的所有分支
git branch -a
```

### 3.3 分支合并：Fast-Forward 与 Three-Way
当你在特性分支上完成了开发，就需要将其合并回主干分支。

```bash
# 1. 先切换回接收修改的目标分支（如 main）
git switch main

# 2. 将 feature-login 分支的改动合并进来
git merge feature-login
```

**合并的两种形式：**
1. **快进合并 (Fast-Forward)**：如果你分出特性分支后，`main` 分支没有任何新的提交，Git 只需要简单地把 `main` 指针向前移动到特性分支的位置。这种合并不会产生新的合并提交。
2. **三方合并 (Three-Way Merge)**：如果在你开发特性期间，`main` 分支也有了其他人的新提交，历史发生了分叉。Git 会找到两个分支的共同祖先，并对两端进行一次三方合并，自动生成一个新的**合并提交（Merge Commit）**。

```bash
# 如果你想强制留下一条清晰的分支线，即使满足快进条件也生成合并提交，可以使用：
git merge --no-ff feature-login
```

### 3.4 清理战场
当分支成功合并后，原本的短期特性分支就完成了它的历史使命，应该及时清理：

```bash
# 删除已被合并的本地分支
git branch -d feature-login

# 强制删除某个分支（即使它里面的某些改动还没被合并，危险操作）
git branch -D feature-failed-experiment
```

## 4. 团队协作：远程仓库与多兵种协同

当开发从单机走向团队，就需要借助远程仓库（Remote Repository）进行代码同步与协同。

### 4.1 远程仓库的管理
如果你是通过 `git clone` 下载的项目，Git 会自动帮你把克隆源地址命名为 `origin`。

```bash
# 查看当前配置的远程仓库别名与对应的 URL 地址
git remote -v

# 手动添加一个新的远程仓库（常用于开源项目 Fork 后保持与原作者同步）
git remote add upstream https://github.com/original-author/repo.git

# 重命名远程仓库别名
git remote rename old_name new_name

# 移除远程仓库关联
git remote remove origin
```

### 4.2 推送与拉取数据
```bash
# 将本地的 main 分支推送到远程 origin 仓库
# -u 参数会建立本地分支与远程分支的“上游追踪关系”，后续直接输入 git push 即可
git push -u origin main

# 后续的极简推送
git push

# 从远程仓库获取最新版本，但【绝不自动合并】到本地当前分支
git fetch origin

# 从远程仓库获取最新版本，并【自动合并】到本地当前分支
git pull origin main
```
> **核心警示**：`git pull` 实际上是 `git fetch` 加上 `git merge` 的组合连续技。在团队频繁提交的环境下，直接 `git pull` 极易由于本地历史分叉而自动产生大量的合并提交，使提交历史交错混乱。建议使用 `git pull --rebase` 来保持历史线性。

## 5. 冲突解决：精准外科手术式代码合并

当两个开发者同时修改了同一个文件的相同行，并且都尝试合并到主干时，Git 无法自动判断哪一份代码是正确答案，此时就会触发**代码冲突 (Conflict)**。

### 5.1 冲突的现场剖析
当发生冲突时，`git merge` 或 `git pull` 命令会中断，终端会打印冲突警告，文件状态会变为 `both modified`。
打开冲突的文件，会看到 Git 为我们标注出了清晰的冲突标记：

```text
<<<<<<< HEAD
    printf("Welcome to the Alpha version!
");
=======
    printf("Welcome to the Release version v1.0!
");
>>>>>>> feature-branding
```
- `<<<<<<< HEAD` 到 `=======` 之间的内容：**你当前分支**（HEAD 所指）里的本地修改。
- `=======` 到 `>>>>>>> feature-branding` 之间的内容：**被合并的分支**（这里指 feature-branding）里的修改。

### 5.2 冲突解决三步法
1. **人工研判与编辑**：与相关同事讨论，或者根据业务逻辑，决定保留哪一段，或者进行重写融合。**手动删掉所有的冲突标记行（`<<<<<<<`, `=======`, `>>>>>>>`）**。
2. **暂存标记**：冲突文件修改完毕并保存后，使用 `git add` 将该文件加入暂存区。这等于向 Git 宣告：“我已手动修复了该文件的冲突”。
3. **完成提交**：执行不带 `-m` 参数的 `git commit`（或输入 `git merge --continue`），Git 会自动打开编辑器让你确认默认的冲突合并信息，保存退出即可。

```bash
# 如果在解决冲突的过程中彻底搞砸了，想撤销整个合并操作，退回到合并前的干净状态：
git merge --abort
```

## 6. 高级重构：历史改写与时光倒流

在代码推送到公共远程仓库**之前**，你可以对本地的提交历史进行任意的润饰、整理和重构，以提供一份干净、逻辑清晰的 Commit 历史供 Code Review。

### 6.1 完美的暂存变基：git rebase
变基（Rebase）是除 Merge 之外的另一种合并分支手段。它的原理是：把你在特性分支上产生的系列提交临时摘下来，移到目标分支的最尖端，然后将这些提交挨个重新应用一遍。

```
变基前：
          A---B (feature)
         /
    C---D (main)

变基后：
          C---D (main)---A'---B' (feature)
```

```bash
# 切换到特性分支
git switch feature-dev

# 将当前分支变基到 main 分支之上
git rebase main
```
**黄金铁律**：**绝不要在公共远程分支上进行 Rebase！** 变基会改写提交的 SHA-1 哈希值。如果你把已经推送到公共服务器的提交给变基了，其他协同开发者在拉取代码时会遭遇历史断层和无休止的冲突，引发灾难。

### 6.2 交互式变基：合并与压缩多个提交
如果你在本地开发时，提交了很多细碎的、“WIP(正在开发中)”、“fix bug 1” 这样的垃圾 Commit，在并入主干前，可以通过交互式变基将它们合并为一个完美的、具备语义化的提交。

```bash
# 针对最近的 4 次提交进行交互式整理
git rebase -i HEAD~4
```
此时 Git 会自动弹出一个文本编辑器，列出这 4 次提交，每行最前面有一个动作命令字（默认是 `pick`）。你可以修改这些命令字：
- `pick (p)`：保留该提交，不做修改。
- `reword (r)`：保留该提交，但允许你修改这次提交的 Commit Message。
- `squash (s)`：保留该提交，但将其内容**压缩并合并到上一个提交中**。
- `drop (d)`：彻底删除这个提交以及里面的代码改动。

修改完保存退出，Git 就会开始按照你的指令编排并重写这部分历史。

### 6.3 挑拣提交：git cherry-pick
有时候，你只需要另一个分支上的**某一个**具体提交（比如一个紧急修复 bug 的 Commit），而不需要把那个分支的全部代码都合并过来。

```bash
# 将指定的 commit 哈希值内容，单独复制并应用合并到当前分支，生成一个新提交
git cherry-pick 7a3b4c9
```

## 7. 时光机救赎：灾难恢复指南

写代码难免会犯错，Git 提供了极强大的回滚机制，无论你处于哪个阶段，都有后悔药可吃。

### 7.1 工作区与暂存区的撤销
```bash
# 场景 1：你在工作区修改了一个文件，还没 add，突然想放弃这些改动，还原成一模一样的原貌
git restore filename.txt

# 场景 2：你写完代码执行了 git add，把修改加到了暂存区，现在想把它从暂存区撤下来（放回工作区）
git restore --staged filename.txt
```

### 7.2 已提交仓库的修正：修补提交
如果你刚刚执行了 `git commit`，突然发现有个错别字没改，或者少 add 了一个小文件，你不想重新制造一个新的 Commit 导致提交历史显得很蠢。

```bash
# 把刚遗漏的文件补上
git add missed_file.txt

# 覆盖并修补上一次提交，它会复用上一次的提交，而不会产生新历史
git commit --amend --no-edit

# 如果你想顺便修改上一次的 commit message：
git commit --amend -m "正确的、更新后的提交信息"
```

### 7.3 重型核武器：git reset
如果要将当前的整个分支回退到过去的某个历史版本，可以使用 `git reset`。它有三种极为关键的模式：

```bash
# 1. --soft 模式（最温和）
# 仅仅把仓库指针（HEAD）移回那个版本。你在这之后的修改全部保留，并直接放在【暂存区】中。
git reset --soft HEAD~1

# 2. --mixed 模式（默认模式）
# 把仓库指针移回。保留之后的修改，但全部放在【工作区】（处于未暂存、未追踪状态）。
git reset --mixed 7a3b4c9

# 3. --hard 模式（极度危险，铁甲熔毁）
# 仓库历史、暂存区、工作区全部强制回退到指定版本。你在那之后的【所有未提交的代码修改将彻底灰飞烟灭】！
git reset --hard 7a3b4c9
```

### 7.4 终极救命稻草：git reflog
如果你不小心执行了 `git reset --hard`，丢失了极其核心的代码，或者在变基时把分支弄丢了。不要惊慌！只要你之前提交过，Git 就会记录你的每一步微小动作。

```bash
# 查看 HEAD 指针在本地的所有移动日志
git reflog
```
你会看到一个详尽的动作列表，类似：
`7a3b4c9 HEAD@{0}: reset: moving to HEAD~1`
`8e4f2a1 HEAD@{1}: commit: feat: 重要功能完成`

找到你丢代码之前的那个 Commit 对应的哈希值（比如 `8e4f2a1`），然后执行：
```bash
git reset --hard 8e4f2a1
```
时光倒流，你的代码完美复活！

## 8. 企业级工作流与 Git 最佳实践

### 8.1 经典 Git Flow 工作流模式
大型企业级团队开发通常会规范分支的职责划分：
- `main / master`：主干分支，仅存放极其稳定的、可直接发布上线的生产环境代码。谢绝一切直接提交。
- `develop`：开发主分支，所有最新的开发成果都汇聚于此。
- `feature/*`：特性/功能开发分支。从 `develop` 切出，开发完毕并通过测试后合并回 `develop`。
- `hotfix/*`：线上紧急修复分支。直接从 `main` 切出修复线上重大 Bug，修复后同时并入 `main` 和 `develop`。

### 8.2 规范化的 Commit Message 格式
良好的提交信息能够极大地提升团队协作效率和项目的可维护性。目前业界广泛采用 **Angular 规范**：

```text
<type>(<scope>): <subject>
```
**高频使用的 Type 类型：**
- `feat`：引入了全新的功能（Feature）。
- `fix`：修复了某个缺陷或 Bug。
- `docs`：仅修改了文档、说明文件（如 README）。
- `style`：代码格式调整，不影响运行逻辑（如空格、缩进、分号补全）。
- `refactor`：代码重构，既不是新增功能也不是修复 Bug。
- `perf`：优化代码以提升性能、响应速度或降低资源消耗。
- `test`：增加、修改单元测试或集成测试代码。
- `chore`：构建工具链、依赖库更新、CI/CD 配置等日常杂务。

**优质示例：**
```text
feat(auth): 支持基于 JWT 的用户登录态持久化校验
```

### 8.3 绝不能忘的 .gitignore 配置文件
在项目根目录下创建一个名为 `.gitignore` 的文本文件，可以告诉 Git 永久忽略哪些不需要（或绝对不能）纳入版本控制的垃圾文件、编译产物和敏感密钥（如 `.env`, `node_modules/`, `__pycache__/`, `target/`, `.DS_Store` 等）。

**`.gitignore` 语法规范示范：**
```text
# 忽略所有扩展名为 .log 的文件
*.log

# 唯独不要忽略特定的这个 log 文件
!important.log

# 忽略当前目录下的 node_modules 文件夹（不包括子目录下的）
/node_modules

# 忽略 build/ 目录下的所有编译产物
build/

# 忽略所有的本地机密配置文件
.env
*.local.pem
```
